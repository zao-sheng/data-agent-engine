# 指标平台方案 vs data-agent-engine：完整架构对比报告

> 版本：v1.0 · 基于当前代码实现（backend 138 单测 + eval 29/29 通过）
> 范围：两种「自然语言 → 指标查询」方案的端到端链路、架构差异、优势短板、适用场景与融合路径

---

## 1. 两种方案的定义

### 1.1 通用指标平台方案（行业主流）

以 Kyligence、Looker、dbt Metrics、阿里 OneData、网易有数等为代表的「指标中台」：

```
NL ──→ LLM 解析成查询参数（指标名 + 维度 + 过滤 + 时间）
        ──→ 检索召回（匹配指标/维度/模型元数据）
        ──→ 调指标平台 Query API
        ──→ 平台查「指标绑定的模型」（建指标/模型时定死表、字段、预聚合）
        ──→ 返回结果
```

**核心特征**：指标与数据模型「预先绑定」——指标创建时指定模型（事实表）+ 字段 + 粒度；查询时平台按绑定关系路由到对应模型/Cube，执行预计算或直接查询。

### 1.2 data-agent-engine 方案（当前实现）

```
NL ──→ term_normalize 黑话归一（poi→门店，确定性）
        ──→ OAG 实体识别（ontology_search 域路由：ord/usr/prd…）
        ──→ ontology_traverse 关系图扩展（join_key/语义/基数）
        ──→ LLM 生成 MQL（结构化中间语言，非参数）
        ──→ mql_validate 校验（schema + 物理渗入检测）
        ──→ mql_explain 确认（confirm_token 工具层强制）
        ──→ 确定性翻译引擎（零 LLM）：
              按粒度/维度/权限动态选表 → 自动 JOIN → 生成标准 SQL
        ──→ execute_sql 只读执行（query_token 绑定 SQL）
```

**核心特征**：指标 = 「公式 + 归属对象」，对象挂多张物理表（DWD/DWS/ADS 各带 `pre_aggregated` 映射）；翻译引擎在查询时**动态决策**选哪张表、拼哪些 JOIN，而非建指标时定死。

## 2. 端到端链路对比（同一查询）

以「华东区数码类产品 GMV，按城市拆分」为例：

| 环节 | 指标平台 | data-agent-engine |
|---|---|---|
| **入口** | NL → LLM 解析参数 | NL → 黑话归一 → OAG 实体识别 |
| **中间表示** | 查询参数 dict（指标/维度/过滤/时间） | **MQL**（结构化语义，含指标族/口径/粒度） |
| **指标解析** | 按名称精确命中平台注册指标 | 指标族三级识别（GMV 支付/下单/消费口径，需澄清时召回） |
| **维度校验** | 指标上**预先声明**的维度白名单，未声明则查不了 | 任意已注册属性 + 关系图 BFS 自动找路径 |
| **选表** | 模型绑定固定（建指标时定死） | 动态：日粒度+预聚合→ADS/DWS；明细/自定义维度→DWD+JOIN |
| **JOIN** | 模型内预定义关系 | 翻译引擎沿关系图**自动生成**（零猜测） |
| **权限** | 平台权限模块 | `user.region_ids` → `F.region_id IN (...)` 注入翻译层 |
| **过滤** | 参数传给平台 | required_filters 自动注入（is_valid=1）+ 用户过滤合并 |
| **执行** | 平台 Query API（可能命中 Cube） | 标准 SQL 直查（sqlite/mysql/doris/hive/sparksql 五方言） |
| **产物** | 结果集（SQL 平台内不可见） | **标准 SQL**（可审计、可下钻、可移植） |

**实际翻译产物**（当前方案，同一个查询）：

```sql
SELECT (SUM(F.pay_amt)) AS gmv,
       R.region_name AS region_name,
       S.city AS city
FROM dwd_ord_pay_di F
JOIN dim_store S   ON S.store_id = F.store_id
JOIN dim_product P ON P.product_id = F.product_id
JOIN dim_region R  ON R.region_id = F.region_id
WHERE F.is_valid = 1                    -- 口径必要过滤（自动注入）
  AND P.product_type = '数码'
  AND F.region_id IN ('R01', 'R02')     -- 行级权限（user.region_ids 注入）
  AND F.dt >= '20260501' AND F.dt <= '20260521'
GROUP BY R.region_name, S.city
```

> 注：此查询因维度 region_name/city 不在 DWS 预聚合表的 available_dims 中，翻译引擎自动降级选 DWD 明细表并拼 3 个 JOIN。若只查日粒度 GMV 无维度，则会选 `ads_ord_gmv_1d`（预聚合，毫秒级）。

## 3. 架构差异的本质

### 3.1 绑定时机：静态（建指标时）vs 动态（查询时）

这是最核心的分野：

| | 指标平台 | data-agent-engine |
|---|---|---|
| 指标↔表关系 | 创建时定死（模型 + 字段 + 粒度） | 指标=公式+归属对象；对象挂多张表，翻译时选 |
| 维度可用性 | 指标上白名单，需预先建模 | 任何已注册属性 + 自动 JOIN 链 |
| 新增表/指标 | 需建模型/Cube + 等物化 | 路径 D 建模 → `ontology_register` 自动采表元数据 → **立即可查** |
| 口径变化 | 改模型/指标 → 发布流程 | 改 YAML/Supabase → reload 即生效 |

### 3.2 语义层：查询参数 vs MQL 中间语言

- 指标平台的 LLM 只做「NL → 参数」抽取，语义理解止步于此，后续全在平台黑盒
- 当前方案 LLM 只生成 MQL（**不生成 SQL、不猜表**），语义校验（validate）、口径确认（explain）、物理翻译（translate）全部是确定性引擎，**LLM 的幻觉被三道闸门拦截**：物理渗入检测、confirm_token 强制确认、query_token 绑定 SQL

### 3.3 透明性：黑盒 vs 可审计

- 指标平台：查询 API 内部逻辑不可见，口径展开（is_valid=1、不含退款冲减）依赖平台元数据展示
- 当前方案：SQL 是翻译产物，**口径展开肉眼可见**（WHERE 里能看到 required_filter 注入），合规审计友好；`mql_explain` 在确认环节展示完整口径 + formula + 版本

## 4. 优势与短板

### 4.1 指标平台的优势（当前方案的短板）

| 优势 | 说明 | 当前方案差距 |
|---|---|---|
| **性能** | 预计算 Cube / 物化视图，毫秒级、高并发 | 每次直查数仓（秒级）；虽有 pre_aggregated 但无预计算层 |
| **成熟治理** | 发布/审批/灰度/下线/多租户/配额 | 简化版（revision 乐观锁 + 可视化审批流待建） |
| **BI 集成** | 对接 Tableau/QuickBI/拖拽分析 | 对话式，无 BI 前端 |
| **缓存与成本控制** | 平台统一查询缓存/限流 | 无查询缓存层 |

### 4.2 data-agent-engine 的优势（指标平台的短板）

| 优势 | 说明 | 指标平台差距 |
|---|---|---|
| **接入速度** | 新表/新指标路径 D → register → 自动采表元数据 → 立即可查，无需等 Cube 物化 | 加指标等半天物化 |
| **长尾探索** | 任意已注册属性组合 + 自动 JOIN 链；explore-fallback 受限兜底 | 「指标没注册就查不了」 |
| **口径透明** | SQL 是翻译产物，口径展开可见，审计友好 | 平台黑盒 |
| **行级权限内嵌** | region_ids 注入在翻译层，不依赖平台权限模块 | 依赖平台权限体系 |
| **多方言可移植** | 同一本体翻译 5 种方言 | 通常锁定自家引擎 |
| **口径歧义处理** | GMV 三口径族三级识别 + 澄清 | 一个指标一个名 |
| **低依赖** | 零外部服务（除可选 Supabase），克隆即跑 | 重型平台部署 |

## 5. 适用场景判断

| 场景 | 推荐 | 理由 |
|---|---|---|
| 固定指标 + 海量数据 + BI 看板 + 毫秒级 | **指标平台** | 预计算 + 治理流 + BI 集成 |
| 快速接入新业务表、口径常变 | **data-agent-engine** | 路径 D 秒级接入，改口径即 reload |
| 长尾即席查询（"这表能算什么"） | **data-agent-engine** | 动态 JOIN + 探索兜底 |
| 合规审计要求口径可追溯 | **data-agent-engine** | SQL 透明，口径展开可见 |
| 团队多人维护 + 审批发布 | **两者都要** | 当前方案已接 Supabase 真源 |
| 报表看板固定口径 | 指标平台 | 稳定 + 快 |
| 对话式数据问答（DSH/IM 内） | **data-agent-engine** | 天生对话流 + confirm 确认 |

## 6. 融合路径（推荐方向）

两者非互斥，可分层互补：

```
┌─────────────────────────────────────────────────────┐
│  NL 层：DSH Agent（对话 / 确认 / 回译）             │
├─────────────────────────────────────────────────────┤
│  语义层：data-agent-engine（OAG → MQL → 校验/确认）│  ← 保留
├─────────────────────────────────────────────────────┤
│  翻译层：data-agent-engine 动态选表/JOIN → 标准 SQL │
├─────────────────────────────────────────────────────┤
│  执行层（二选一/可切换）：                           │
│    A. 直查数仓（现状，秒级）                        │
│    B. 指标平台执行引擎/Cube（接入 Query API，毫秒级）│  ← 增强
└─────────────────────────────────────────────────────┘
```

- **方案 A（推荐先做）**：把当前方案的 `_executor` 替换为指标平台 Query API 适配器——NL→MQL→SQL 不变，执行交给平台 Cube，白拿性能与缓存。语义层保留（动态 JOIN、口径透明），执行层复用平台基建
- **方案 B（治理互补）**：用当前方案的 Ontology（YAML/Supabase）作为指标平台的元数据源，平台负责发布/审批/可视化，引擎负责即席长尾

---

## 7. 结论

> **指标平台是「把指标做成产品」——建指标时绑定模型，牺牲灵活性换性能与治理；
> data-agent-engine 是「把口径做成可推导的语义」——查询时动态解析，牺牲预计算换动态覆盖与透明。**

两者核心差异 = **绑定时机**（静态 vs 动态）× **语义层位置**（参数 vs MQL）× **透明性**（黑盒 vs 可审计）。
当前方案的 `pre_aggregated` 机制已具备「预聚合优先」的雏形，补齐执行层（Cube 接入）即兼具两者优势。
