# 建模全流程（需求 → 上线 → 治理）

> 触发：用户提出**建模类需求**（新建表 / 新建指标 / 改表结构 / 改 ETL 逻辑 / 注册本体）。
> 核心原则：**每个阶段先产出逻辑报告 → 用户确认 → 才调用 MCP/skill 真实执行**。
> 标准模板见下方「需求识别提取模板」与「方案书模板」；信息缺失时与用户多轮澄清，不得臆造。

## 阶段总览（顺序执行，不可跳步）

| 阶段 | 产出物 | 确认点 |
|------|--------|--------|
| 0 需求分析 | 需求识别提取表（可编辑草稿） | 逐项确认：口径/指标/维度/来源/时效，用户可改 |
| 1 方案设计 | 建模方案书（含变更评估，可编辑） | 变更清单逐项确认，用户可增删改 |
| 2/3 方案落地 | **配对 DDL+ETL 列表**（modeling_plan）+ 本体注册项 | 每对 DDL/ETL 确认（N 表=N 对）；注册项确认 |
| 4 测试 | 测试报告 | 测试结论确认 |
| 5 上线 | 发布记录 | 上线确认 |
| 6 调度 | 调度配置 | 调度参数确认 |
| 7 SLA/DQC | 治理配置 | SLA/DQC 规则确认 |

## 阶段 0：需求分析（先识别，后澄清，**可编辑清单**）

1. 读取需求文档（用户提供 URL / 文本 / 附件）。
2. 用下方**需求识别提取模板**逐项提取；**缺失项标记 ❓**，不猜测。
   - 每项标注**来源**：`需求文档` / `用户input` / `待确认`——需求文档明确项标注出处，
     用户口头补充项标注 input，两者都没有才标待确认。
3. 与用户多轮澄清补齐缺失项（口径、粒度、来源、时效、产出形态）。
4. **清单确认协议（必须遵守，禁止逐项弹选择题）**：
   1. 一次性输出完整的「需求识别提取表」文本（markdown 表格，**每行带编号**）；
   2. 调用**一次** `ask_user_question`，问题格式固定为：
      「以上需求识别表请**整体确认**，或指出**要修改的项（编号 + 新内容）**」，
      选项：`[整体确认 (Recommended), 我要修改（回复编号+新值）, 增补信息]`；
   3. 用户回复修改项 → 更新草稿 → 重新输出完整清单 → 再确认，直到整体确认；
   4. **禁止**把同一清单拆成多次单问选择题（每次只问一项、给固定选项）。
5. 用户整体确认后的需求表 = 阶段 1 的输入，**后续阶段如与需求表冲突以需求表为准**。

### 需求识别提取模板
```
# 建模需求识别表（草稿，可编辑）
| # | 项 | 内容 | 来源 | 状态 |
|---|----|------|------|------|
| 1 | 需求编号/名称 | | 需求文档/用户input/待确认 | ✅/❓ |
| 2 | 需求背景与业务目标 | | | |
| 3 | 业务口径（指标定义、计算逻辑） | | | |
| 4 | 涉及指标 | | | |
| 5 | 分析维度（门店/区域/渠道/用户…） | | | |
| 6 | 时间粒度（日/周/月/季/年） | | | |
| 7 | 数据来源（上游系统/表） | | | |
| 8 | 产出形态（新表/新字段/新指标/报表） | | | |
| 9 | 更新频率与时效（T+1/实时） | | | |
| 10 | 数据量级估算 | | | |
| 11 | SLA 要求（产出时间点） | | | |
| 12 | 数据质量要求（DQC） | | | |
| 13 | 干系人/负责人 | | | |
```
> 编辑规则：所有项均可改；用户未提修改的项保持草稿值；❓ 项必须补齐才能进入阶段 1。

## 阶段 1：方案设计（评估现状 → 出方案书，**可编辑清单**）

1. **查重**：`mcp__dataagent__ontology_search` 检查目标对象/指标/表是否已存在。
2. **现状对照**：结合 `warehouse-standards` 规范与现有 Ontology，逐项判定：
   - **完全新增**：新表/新对象/新指标（需 DDL + ETL + 本体注册）
   - **新增字段**：既有表加列（DDL ALTER + ETL 改造 + 本体属性注册）
   - **修改逻辑**：既有 ETL 口径/逻辑变更（ETL 改造，无 DDL）
   - **本体注册**：既有表/字段映射入 Ontology（无 DDL/ETL，仅注册）
3. **清单确认协议（必须遵守，禁止逐项弹选择题）**：
   1. 一次性输出完整的「建模方案书」文本（变更清单每行带编号）；
   2. 调用**一次** `ask_user_question`：
      「以上方案书请**整体确认**，或指出**要修改的变更项（编号 + 新内容）**」，
      选项：`[整体确认 (Recommended), 修改变更项（回复编号+新值）, 增删变更]`；
   3. 用户回复修改 → 更新方案书 → 重新输出完整清单 → 再确认，直到整体确认；
   4. **禁止**把变更清单拆成多次单问选择题。
4. 用户整体确认的方案书 → 进入阶段 2/3（用 `modeling_plan` 一次生成全部 DDL+ETL）。

### 方案书模板
```
# 建模方案书
## 1. 需求摘要（引用阶段 0 确认表）
## 2. 现状分析（查重结果 + 现有表/对象/指标清单）
## 3. 模型变更评估
| # | 变更类型 | 对象/表 | 变更内容 | 依据 |
|---|---------|---------|---------|------|
| 1 | 完全新增 | | | |
| 2 | 新增字段 | | | |
| 3 | 修改逻辑 | | | |
| 4 | 本体注册 | | | |
## 4. 设计明细（对应变更清单逐项）
### 变更 1：<对象> 完全新增
- 表结构（Spark SQL DDL）
- ETL 逻辑（Spark SQL）
- 本体注册项（对象/指标/属性/关系）
## 5. 测试方案（数据验证口径 + Golden 用例）
## 6. 上线计划（依赖/窗口/回滚）
## 7. 调度与治理（cron / SLA / DQC 初稿）
## 8. 风险与待确认项
```

## 阶段 2/3：方案落地（DDL + ETL **配对生成**，用 modeling_plan）

按方案书确认的变更清单，**一次性**调用 `mcp__dataagent__modeling_plan` 生成
配对的 DDL+ETL 列表：
1. **变更清单 → modeling_plan**：把方案书第 3 节的每个变更逐项传入
   `{type, obj_name, layer, domain, subject, metrics, dimensions}`。
   `domain` 缺省取对象自身业务域（本体治理字段，如 ord/prd/usr）——
   跨域新建才需显式传 domain。
2. **配对校验**：工具返回的 `summary.paired` 必须为 True——新增/加字段事实表
   **必须 DDL 与 ETL 成对**（N 张表 → N 对）；`errors` 非空时先解决再继续。
   > 严禁分开发 ddl_generate / etl_generate 造成数量不对应（2 个 DDL 配 1 个 ETL）。
3. **清单确认协议**：一次性输出所有 {DDL, ETL} 对的清单文本（每对带编号），
   一次 `ask_user_question`：「请整体确认，或指出要修改的对（编号+新值）」；
   **禁止**每对单独弹确认。
4. **本体注册（双通道）**：变更清单中 type=register 的项 →
   调用 `mcp__dataagent__ontology_register`（kind=object/function/relation/glossary/
   config，entry=YAML 条目结构）→ 展示注册项清单（编号）→ 一次整体确认 → 写入。
   - 写入目标由 `DATA_AGENT_ONTOLOGY_STORE` 决定：yaml=发布基线文件 /
     supabase=多人编辑真源（revision 乐观锁）；
   - **合并语义**（重要）：已存在条目为合并更新（**省略字段保留原值**，
     可只提交要改的字段）；新建条目缺省字段落库默认值（status=active、
     object_type=fact、version=v1.0）；**更新 function 必须携带 formula/owner**
     （NOT NULL 列）；更新 object 无必填限制。
   - **字段级校验**：register 写入前校验格式（pre_aggregated 必须是字典、
     required_filters 必须是列表等），非法值返回字段级 400 错误——不要重试
     写非法条目，按错误提示修正 entry 后重试。
   - Supabase 模式注册后建议 `ontology_export` 导出 YAML 走评审闭环；
   - sqlite 是只读产物，拒绝写入（提示写 YAML 后重新 `ontology_compile`）。
5. 依赖检查：目标表依赖的明细/维表已存在（ontology_search 复核）。

## 阶段 4：测试

1. 产出测试计划：Golden 用例（口径断言）+ 数据质量检查（空值/主键唯一/行数波动）。
2. 执行测试（沙箱/样例库）→ 产出**测试报告**（含用例清单、通过/失败、口径一致性结论）。
3. 清单确认协议：一次输出测试报告全文 → 一次 `ask_user_question` 整体确认 → 才可上线。

## 阶段 5：上线

1. 产出发布记录：变更清单、DDL 执行记录、ETL 部署记录、回滚方案。
2. 清单确认协议：一次输出发布记录 → 一次整体确认 → 执行发布。

## 阶段 6：调度配置

1. `mcp__dataagent__scheduler_submit`（接入平台后真实提交；当前为预留）。
2. 产出调度配置（cron 表达式、任务依赖、告警通道、幂等键）→
   清单确认协议：一次输出配置全文 → 一次整体确认。

## 阶段 7：SLA / DQC 配置

1. 产出治理配置：
   - **SLA**：产出时间点、延迟告警阈值、责任人
   - **DQC**：空值率、主键唯一性、同环比波动阈值、口径校验规则
2. 清单确认协议：一次输出治理配置全文 → 一次整体确认 → 登记
   （预留：接入数据质量平台后自动登记）。

## 清单确认协议（全局统一，所有确认环节必须遵守）

```
① 先输出完整清单（markdown，每项带编号），一次展示全部内容；
② 再调用【一次】ask_user_question，问题格式：
   「以上清单请整体确认，或指出要修改的项（编号+新内容）」；
   options: [整体确认 (Recommended), 我要修改（回复编号+新值）, 增补信息]；
③ 用户回复修改 → 更新清单 → 重新输出全文 → 再整体确认，直到确认；
④ 禁止把同一清单拆成多次单问选择题；禁止每次只展示一项。
```

## 硬性规则
- **每个阶段先出报告（完整清单）、用户整体确认后才执行**；用户拒绝则停止并记录原因。
- 所有确认必须走**清单确认协议**（先输出完整清单 → 一次整体确认），
  不得逐项弹选择题、不得把一次确认拆成多次提问。
- 信息缺失必须澄清（❓ 项不得臆造），宁缺毋滥。
- 所有 DDL/ETL/注册/调度/治理变更全程留痕（审计日志）。
- 命名遵守 `warehouse-standards`；新建对象/指标必须注册 Ontology 才能被查询。
