# 建模全流程（需求 → 上线 → 治理）

> 触发：用户提出**建模类需求**（新建表 / 新建指标 / 改表结构 / 改 ETL 逻辑 / 注册本体）。
> 核心原则：**每个阶段先产出逻辑报告 → 用户确认 → 才调用 MCP/skill 真实执行**。
> 标准模板见下方「需求识别提取模板」与「方案书模板」；信息缺失时与用户多轮澄清，不得臆造。

## 阶段总览（顺序执行，不可跳步）

| 阶段 | 产出物 | 确认点 |
|------|--------|--------|
| 0 需求分析 | 需求识别提取表（可编辑草稿） | 逐项确认：口径/指标/维度/来源/时效，用户可改 |
| 1 方案设计 | 建模方案书（含变更评估，可编辑） | 变更清单逐项确认，用户可增删改 |
| 2/3 方案落地 | **配对 DDL+ETL 列表**（modeling_plan）+ 本体注册项 | 每对 DDL/ETL 确认（N 表=N 对）；注册项确认 |
| 4 测试 | 测试报告 | 测试结论确认 |
| 5 上线 | 发布记录 | 上线确认 |
| 6 调度 | 调度配置 | 调度参数确认 |
| 7 SLA/DQC | 治理配置 | SLA/DQC 规则确认 |

## 阶段 0：需求分析（先识别，后澄清，**可编辑**）

1. 读取需求文档（用户提供 URL / 文本 / 附件）。
2. 用下方**需求识别提取模板**逐项提取；**缺失项标记 ❓**，不猜测。
   - 每项标注**来源**：`需求文档` / `用户input` / `待确认`——需求文档明确项标注出处，
     用户口头补充项标注 input，两者都没有才标待确认。
3. 与用户多轮澄清补齐缺失项（口径、粒度、来源、时效、产出形态）。
4. 产出「需求识别提取表」（**草稿**）→ 展示给用户 → **逐项确认/编辑**：
   - 用户可修改任意项（如改口径、换粒度、增删指标维度、改数据来源）；
   - 用户指出修改 → 更新草稿 → 重新展示 → 直到用户确认。
5. 用户确认后的需求表 = 阶段 1 的输入，**后续阶段如与需求表冲突以需求表为准**。

> 编辑规则：所有项均可改；用户未提修改的项保持草稿值；❓ 项必须补齐才能进入阶段 1。

## 阶段 1：方案设计（评估现状 → 出方案书，**可编辑**）

1. **查重**：`mcp__dataagent__ontology_search` 检查目标对象/指标/表是否已存在。
2. **现状对照**：结合 `warehouse-standards` 规范与现有 Ontology，逐项判定：
   - **完全新增**：新表/新对象/新指标（需 DDL + ETL + 本体注册）
   - **新增字段**：既有表加列（DDL ALTER + ETL 改造 + 本体属性注册）
   - **修改逻辑**：既有 ETL 口径/逻辑变更（ETL 改造，无 DDL）
   - **本体注册**：既有表/字段映射入 Ontology（无 DDL/ETL，仅注册）
3. 产出「建模方案书」（**草稿**）→ 展示给用户 → **逐项确认/编辑**：
   - 变更清单每一行可编辑（变更类型/对象/表名/指标/维度）；
   - 用户可增删变更项、调整对象或指标维度；
   - 编辑后重新出方案书，直到用户确认。
4. 用户确认的方案书 → 进入阶段 2（用 `modeling_plan` 一次生成全部 DDL+ETL）。

### 方案书模板
```
# 建模方案书
## 1. 需求摘要（引用阶段 0 确认表）
## 2. 现状分析（查重结果 + 现有表/对象/指标清单）
## 3. 模型变更评估
| # | 变更类型 | 对象/表 | 变更内容 | 依据 |
|---|---------|---------|---------|------|
| 1 | 完全新增 | | | |
| 2 | 新增字段 | | | |
| 3 | 修改逻辑 | | | |
| 4 | 本体注册 | | | |
## 4. 设计明细（对应变更清单逐项）
### 变更 1：<对象> 完全新增
- 表结构（Spark SQL DDL）
- ETL 逻辑（Spark SQL）
- 本体注册项（对象/指标/属性/关系）
## 5. 测试方案（数据验证口径 + Golden 用例）
## 6. 上线计划（依赖/窗口/回滚）
## 7. 调度与治理（cron / SLA / DQC 初稿）
## 8. 风险与待确认项
```

## 阶段 2/3：方案落地（DDL + ETL **配对生成**，用 modeling_plan）

按方案书确认的变更清单，**一次性**调用 `mcp__dataagent__modeling_plan` 生成
配对的 DDL+ETL 列表：
1. **变更清单 → modeling_plan**：把方案书第 3 节的每个变更逐项传入
   `{type, obj_name, layer, domain, subject, metrics, dimensions}`。
2. **配对校验**：工具返回的 `summary.paired` 必须为 True——新增/加字段事实表
   **必须 DDL 与 ETL 成对**（N 张表 → N 对）；`errors` 非空时先解决再继续。
   > 严禁分开发 ddl_generate / etl_generate 造成数量不对应（2 个 DDL 配 1 个 ETL）。
3. **逐项确认**：每对 {DDL, ETL} 展示给用户确认；用户可编辑（改表名/指标/维度
   → 重新 modeling_plan）。
4. **本体注册**：变更清单中 type=register 的项 → 编辑 `backend/ontology/`
   （objects/functions/relations/glossary）→ 展示注册项 → 用户确认 → 写入。
5. 依赖检查：目标表依赖的明细/维表已存在（ontology_search 复核）。

## 阶段 4：测试

1. 产出测试计划：Golden 用例（口径断言）+ 数据质量检查（空值/主键唯一/行数波动）。
2. 执行测试（沙箱/样例库）→ 产出**测试报告**。
3. 测试报告含：用例清单、通过/失败、口径一致性结论 → 用户确认后才可上线。

## 阶段 5：上线

1. 产出发布记录：变更清单、DDL 执行记录、ETL 部署记录、回滚方案。
2. 用户确认 → 执行发布。

## 阶段 6：调度配置

1. `mcp__dataagent__scheduler_submit`（接入平台后真实提交；当前为预留）。
2. 产出调度配置：cron 表达式、任务依赖、告警通道、幂等键 → 用户确认。

## 阶段 7：SLA / DQC 配置

1. 产出治理配置：
   - **SLA**：产出时间点、延迟告警阈值、责任人
   - **DQC**：空值率、主键唯一性、同环比波动阈值、口径校验规则
2. 用户确认 → 登记治理配置（预留：接入数据质量平台后自动登记）。

## 硬性规则
- **每个阶段先出报告、用户确认后才执行**；用户拒绝则停止并记录原因。
- 信息缺失必须澄清（❓ 项不得臆造），宁缺毋滥。
- 所有 DDL/ETL/注册/调度/治理变更全程留痕（审计日志）。
- 命名遵守 `warehouse-standards`；新建对象/指标必须注册 Ontology 才能被查询。
